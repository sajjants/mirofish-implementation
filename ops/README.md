# ops: local wrapper around upstream MiroFish

This directory runs the real [MiroFish](https://github.com/666ghj/MiroFish) on your own machine with a local LLM, and adds scripts that enforce limits, privacy and repeatability around it. Upstream lives untouched in `../mirofish`, pinned in `UPSTREAM.md`; the only changes to it are the two re-applicable patches in `patches/`.

> **Read this first.**
> - **Nothing here is validated against real outcomes.** No run has been compared with what actually happened in any real situation. A MiroFish run is a story generated by a language model playing social-media users, not a forecast.
> - **Local models weaken persona quality.** A 30B quantised model run on a laptop gives flatter, more repetitive personas than the large cloud models MiroFish was built for. It follows formats less reliably and invents figures, dates and events (see `INJECTION_TEST.md` and the factguard output of any run).
> - With 2–3 runs per question, differences between runs may be chance. Treat outputs as a handful of samples from a noisy generator.

## Quick start for a new teammate

1. **Prerequisites:** macOS or Linux (Windows via WSL), Git, uv, Node.js 18+, `lsof`, Ollama, and about 24 GB of GPU or unified memory. With less, first pick a smaller `HF_MODEL_REF` in `config/model.conf` (section 2).
2. **Clone into a folder that no sync or backup tool uploads** (not Google Drive, iCloud, Dropbox or OneDrive).
3. **Run the setup:** `ops/scripts/bootstrap.sh --with-models` (about 19 GB of models plus about 1.1 GB of cached assets; safe to re-run).
4. **Check `ops/scripts/doctor.sh` passes**, in particular the JSON compliance check.
5. **Start:** `ops/scripts/ollama_serve.sh`, then `ops/scripts/start.sh --no-frontend`. **Stop:** `ops/scripts/stop.sh --ollama`.
6. **Run a pilot** with your own seed and questions (sections 4–6). Seeds, runs, mappings, logs and `.env` are git-ignored, so nothing private comes with the clone.

The time estimates in `config/limits.yaml` come from an M3 Max; the pilot re-measures them on your machine. MiroFish is AGPL-3.0 and `patches/` modify it, which is fine for private use; read the licence notes in `NOTES.md` before running it as a service for others.

Status: Phases 1–6 complete. 82 wrapper tests pass. The Phase 5 checks on the real stack are recorded under "Verification" below.

## 1. Install

Requirements: macOS or Linux (Windows via WSL), Git, [uv](https://docs.astral.sh/uv/), Node.js 18+, `lsof`, [Ollama](https://ollama.com/download) (on your `PATH`, at `.tools/ollama/current/ollama`, or set `OLLAMA_BIN` in `config/model.conf`), and about 24 GB of GPU or unified memory for the default model (pick a smaller one in step 2 otherwise).

**Clone into a folder that no sync or backup tool uploads.** That rules out folders backed up by Google Drive for Desktop (for example `~/Documents` or `~/Desktop`), iCloud Drive, Dropbox and OneDrive. Every seed, run, report and pseudonym mapping lives under this folder, and nothing in this wrapper can stop a sync client from uploading it. `start.sh` and `doctor.sh` warn when they detect a synced location, but detection is heuristic.

```bash
mkdir -p ~/dev && cd ~/dev     # any non-synced location
git clone https://github.com/sajjants/mirofish-implementation.git && cd mirofish-implementation
ops/scripts/bootstrap.sh --with-models
```

`bootstrap.sh` is idempotent. It does the following:
- Clones upstream at the pinned commit and refuses any other commit.
- Applies `patches/`.
- Installs only from the lockfiles (`uv sync --frozen`, `npm ci --ignore-scripts`) and never runs upstream's own setup scripts.
- Writes `mirofish/.env` from `config/mirofish.env.example` (mode 0600).
- Caches the two files the simulation would otherwise download at runtime (about 1.1 GB; `--skip-assets` defers this) and switches `.env` to offline mode.
- Runs the tests.
- With `--with-models`, pulls the models and runs `doctor.sh`.

## 2. Pull the model

The model is a variable, not a hard-coded choice. Edit `config/model.conf`:

| Key | Default | Meaning |
|---|---|---|
| `HF_MODEL_REF` | `hf.co/unsloth/Qwen3-30B-A3B-Instruct-2507-GGUF:Q4_K_M` | Chat model pulled through Ollama. Size guide in the file: 24 GB+ → 27–32B, 16 GB → 14B, 8–12 GB → 8B. Verify the repo and quant on huggingface.co before pulling. |
| `NUM_CTX` | `32768` | Context baked into the derived model (minimum 16384). MiroFish cannot pass it per request. |
| `EMBED_MODEL_REF` | `hf.co/Qwen/Qwen3-Embedding-0.6B-GGUF:Q8_0` | Embeddings for the local memory store. |
| `OLLAMA_HOST` | `127.0.0.1:11434` | Must be loopback; `ollama_serve.sh` refuses anything else. |

```bash
ops/scripts/ollama_serve.sh     # Ollama on 127.0.0.1:11434, cloud models disabled
ops/scripts/build_model.sh      # pulls both GGUFs, creates aliases mirofish-llm and mirofish-embed with NUM_CTX
ops/scripts/doctor.sh           # loopback bind, memory, model, context, 5 JSON prompts, throughput, embeddings
```

`doctor.sh` must pass before a batch is worth running. The JSON compliance check matters most: a model that fails it will break MiroFish's ontology, persona and config stages.

## 3. Start and stop the stack

```bash
ops/scripts/start.sh --no-frontend   # backend 127.0.0.1:5001 (+ LLM meter 127.0.0.1:11435); omit the flag for the UI on 127.0.0.1:3000
curl -s http://127.0.0.1:5001/health
ops/scripts/stop.sh                  # backend, frontend, meter and simulation subprocesses (--ollama: Ollama too)
```

`start.sh` refuses to start, or stops everything again, in any of these cases:
- `FLASK_HOST`, `LLM_BASE_URL`, `LLM_BOOST_BASE_URL` or the embedding URL is not loopback.
- `MIROFISH_MEMORY_BACKEND` is not `local`.
- Any tracing key (LangSmith, Langfuse, OTEL, …) is enabled.
- `FLASK_DEBUG` is on.
- Ollama or any started process listens on a non-loopback address.

It also scrubs tracing, proxy and LLM variables from the environment, so `.env` alone decides what the backend sees. Run `stop.sh` from a normal terminal: if it cannot read a process's command line (some sandboxes hide it), it keeps the PID file and exits non-zero rather than guessing.

## 4. Write the seed and questions

Keep real inputs in `ops/seeds/` (git-ignored). The format is shown in `examples/seed.md` and `examples/questions.md`:

- **Seed:** each fact is a line tagged `VERIFIED:`, `ESTIMATE:`, `BELIEF:` or `UNKNOWN:`. Only facts are needed; leave out verbatim third-party text, which is the main injection risk.
- **Questions:** `## Q1`, `## Q2`, `## Q3` sections, each with the question and any horizon or context.
- **Optional terms file**, to pseudonymise names before upload (see `pseudonymize.py --help`):

  ```text
  person: Elena Duarte | Duarte
  org:    Riverton Transit Workers Union | the union's leadership
  place:  Riverton
  ```

  `pseudonymize.py --suggest ops/seeds/seed.md` lists capitalised phrases to consider. Currency amounts and numbers ≥ 100 are scaled by a secret factor.

## 5. Run a pilot

A batch is one seed with its questions. Use a batch id such as `B1` (letters, digits and dashes).

```bash
ops/scripts/prepare_inputs.py --batch B1 --seed ops/seeds/seed.md --questions ops/seeds/questions.md \
    --terms ops/seeds/terms.txt                     # optional; lints the seed and prints what it removed
ops/scripts/unknown_variants.py propose --batch B1   # 3-5 alternatives per UNKNOWN; review/edit ops/runs/B1/alternatives.json
ops/scripts/plan.py --batch B1                       # first plan, from default estimates
ops/scripts/start.sh --no-frontend
ops/scripts/run_batch.py pilot --batch B1            # Q1, 10 rounds, then STOPS
```

The pilot prints:
- the measured LLM calls, wall-clock time, structured-output failure rate and agent count;
- the cost model it derived;
- the re-computed plan for the real runs, with any cuts it made.

Check the agent count: every typed entity in the graph becomes an agent and upstream has no cap. If there are too many, trim the seed and prepare a new batch.

## 6. Run Q1–Q3 from your questions.md

```bash
ops/scripts/run_batch.py run --batch B1 --confirm    # every planned run, for every question
ops/scripts/run_batch.py status --batch B1           # progress, from another terminal
ops/scripts/factguard.py --batch B1                  # flags unsupported claims (uses the local LLM for UNKNOWN stances)
ops/scripts/compare.py --batch B1                    # trajectories, resistors, UNKNOWN tables, noise warnings
```

What `run` does:
- **Plan:** each question gets `runs.per_question` runs (2), or `per_question_high_unknown` (3) when the seed has more than `unknown_threshold` UNKNOWN facts. Each run has 30 rounds, cut toward 20 and then to fewer runs if the caps would be exceeded.
- **Variants:** each run uses one seeded variant: every UNKNOWN is replaced by one sampled alternative, balanced so that runs cover different alternatives.
- **Caps:** `run` checks the caps against measured usage before each run and does not start runs that would exceed them.
- **Resume:** you can interrupt with Ctrl-C, a crash or a reboot, then re-run the same command. Finished runs are skipped. An unfinished run continues after its last completed stage, and if its simulation is still running in MiroFish it is not restarted.
- **One batch at a time:** a second batch refuses to start, because calls are attributed to runs by time window. Do not use the MiroFish UI for other work while a batch runs.

Expect roughly 12–15 minutes per 30-round run with 9 agents on an M3 Max (the measured `example-3` batch: 473 calls in 55 minutes for 4 runs, against an estimate of 467 calls and 59 minutes).

## 7. Read the outputs

Everything is under `ops/runs/` (directories 0700, files 0600, git-ignored).

Per batch, `ops/runs/B1/`:

| File | Contents |
|---|---|
| `inputs.json`, `inputs/` | Parsed facts, UNKNOWNs, questions, lint findings, hashes; the uploaded seed and each question's requirement text |
| `alternatives.json`, `variants.json`, `variants/` | UNKNOWN alternatives, the sampled variants (RNG seed recorded), each variant's seed |
| `pilot.json`, `plan.json`, `batch.json` | Pilot measurements, the confirmed plan, per-run status |
| `compare.md` / `.json` | Trajectory counts per question, main resistors, UNKNOWN value × trajectory tables, warnings |

Per run, `ops/runs/B1_q1_r1/` (the pilot is `B1_pilot`):

| File | Contents |
|---|---|
| `manifest.json` | Upstream commit and patch hashes, ops commit, model name and digests, limits, seed and variant hashes, variant mapping, MiroFish ids, per-stage timings and metered calls |
| `report.md` | MiroFish's report (pseudonymised if the batch was) |
| `transcript.json` | Agents, their generated stances, and every post and comment on both platforms |
| `factguard.md` / `.json` | Flags: unsupported numbers, dates and entities (report and posts), inactive actors, UNKNOWN stances that contradict the run's variant |
| `report.annotated.md` | The report with `**[FLAG]**` after each flagged item |
| `report.depseudo.md`, `transcript.depseudo.json` | De-pseudonymised copies (pseudonymised batches only) |

How to read them:
- Start with `compare.md`, then read the transcripts of a few runs. The agents' posts are what was simulated.
- `report.md` is written afterwards by a report agent that searches the graph. It regularly states things no agent did (`INJECTION_TEST.md`), which is why `compare.py` classifies transcripts rather than reports.
- A factguard flag means "check this", not "this is false".
- Upstream starts the simulated day at 00:00. The wrapper shifts each run's schedule so round 1 is 08:00 (`limits.yaml` `simulation.clock_start_hour`). Log timestamps in MiroFish's own files still read as if the day started at midnight.

## 8. De-pseudonymise

`factguard.py` and `compare.py` de-pseudonymise automatically when the batch used `--terms`. For any other file:

```bash
ops/scripts/depseudonymize.py --mapping ops/mappings/B1.mapping.json ops/runs/B1_q1_r1/report.md   # -> report.depseudo.md
```

Names and figures that appear verbatim are restored. Figures the model computed itself (sums, rounded values) cannot be mapped back. They are listed at the end so you know they are on the pseudonymised scale; divide by the mapping's `scale_factor`. Keep `ops/mappings/` private, because it holds the originals.

## 9. Purge

```bash
ops/scripts/purge.sh B1_q1_r1            # one run
ops/scripts/purge.sh B1 --batch          # every run of the batch, its inputs and its mapping
ops/scripts/purge.sh B1 --batch --logs   # also every backend and ops log (stop MiroFish first)
```

Purging removes each run's MiroFish project, simulation and report directories, its graph in the local store (SQLite with `secure_delete`), and its `ops/runs/` directory. Files are overwritten with zeros and fsynced before deletion.

On SSDs and copy-on-write filesystems (APFS), overwriting does not guarantee the old blocks are gone. Full-disk encryption (FileVault) is what protects deleted data there.

If purge warns that a file "has 2 hard links", another program holds a second link to the same data. Purge then unlinks the file without overwriting it, so the other copy is left intact. On this machine the other link was in Google Drive's upload staging folder (`~/Documents/.tmp.driveupload`), which means the file was queued for upload. Purge cannot reach copies that are already in the cloud.

## 10. Constraints and how each is enforced

"Config" means a setting in `.env`, `model.conf` or `limits.yaml`. "Wrapper" means a script in `ops/scripts/` checks or does it. "Patch" means one of the two upstream patches. "Not enforceable" means it cannot be guaranteed without changing MiroFish internals.

| Constraint | Enforced by | How, and what is not covered |
|---|---|---|
| Upstream pinned and unmodified | Wrapper | `bootstrap.sh` and `apply_patches.sh` check out and verify the commit in `UPSTREAM.md` and refuse a different one. All changes are in `patches/0001` and `0002`. |
| Dependencies pinned to lockfiles, no upgrades | Wrapper | `uv sync --frozen`, `npm ci --ignore-scripts`; upstream's install scripts are never run. |
| Seed content does not leave the machine | Config + patch + wrapper | Local LLM (`LLM_BASE_URL` loopback) and local memory store (patch 0001 replaces Zep Cloud). `start.sh` refuses non-loopback URLs and any memory backend other than `local`. `netcheck.sh` proves it per pilot for MiroFish's processes. **Not covered:** other programs on the machine, above all cloud sync and backup clients. `start.sh` and `doctor.sh` only warn when the project folder looks synced. |
| LLM is local, via Ollama, model as an editable variable | Config | `model.conf` `HF_MODEL_REF`; `.env` `LLM_MODEL_NAME=mirofish-llm`. |
| `num_ctx` ≥ 16k | Config + wrapper | Baked into the Ollama Modelfile (32768); `doctor.sh` checks it. |
| Ollama binds 127.0.0.1 only | Wrapper | `ollama_serve.sh` refuses a non-loopback `OLLAMA_HOST`; `start.sh` and `doctor.sh` fail if Ollama listens elsewhere. An Ollama you start yourself is only checked, not controlled. |
| `doctor.sh`: reachability, memory, model, JSON compliance | Wrapper | 5 JSON prompts, pass rate reported. |
| Zep Cloud only with a pseudonymised seed | Wrapper | Zep Cloud is not used (local store chosen in Phase 2). `start.sh` refuses a non-local backend. `run_batch.py` also refuses an un-pseudonymised batch if the backend is not local. |
| Backend and frontend bind 127.0.0.1 | Config + patch + wrapper | `.env` `FLASK_HOST=127.0.0.1`; `start.sh` runs Vite with `--host 127.0.0.1` and verifies the listening sockets after start. Patch 0002 adds CORS and Host-header allowlists (against DNS rebinding from a browser). Docker: `docker/compose.local.yml` publishes on 127.0.0.1 only (**untested**, Docker not installed here). |
| No telemetry or tracing | Config + patch + wrapper | `start.sh` scrubs tracing variables and refuses enabled tracing keys. It sets `HF_HUB_DISABLE_TELEMETRY=1` and `DO_NOT_TRACK=1`; `.env` has `HF_HUB_OFFLINE=1`. Patch 0002 removes Google Fonts. No analytics were found in the frontend (`NOTES.md`). |
| `netcheck.sh` fails on any non-loopback connection not in `allowed_hosts.txt` | Wrapper | Python audit hook in the backend and simulations, plus per-second `lsof` sampling of all MiroFish processes and Ollama. `allowed_hosts.txt` is empty. A non-Python child process would be seen only by `lsof` sampling. |
| Docker on an internal network without egress | Wrapper (untested) | `docker/compose.local.yml`. No Neo4j: the local store is SQLite inside the backend. |
| Seeds, outputs, logs created 0700 | Wrapper | `start.sh` runs with `umask 077`; scripts create `ops/` data directories 0700 and files 0600. MiroFish's own `mirofish/backend/uploads/` is created by upstream; under `start.sh` it inherits the umask. |
| `purge.sh RUN_ID` securely deletes run data | Wrapper | See section 9 for the SSD caveat. Log files are not separable per run (`--logs` removes all). |
| Seed treated as untrusted (injection) | Wrapper (partial) | `prepare_inputs.py` strips HTML comments and lines that address a model. **Not enforceable without changing internals:** any assertion in the seed can become a graph fact that personas and the report repeat. Result in `INJECTION_TEST.md`. |
| Pseudonymise / de-pseudonymise | Wrapper | `pseudonymize.py` refuses output that still contains an original term. The mapping is 0600 in git-ignored `mappings/`. |
| Per-question uploads and requirement text via REST | Wrapper | `prepare_inputs.py`, `mirofish_api.py` drive all five stages through the API. |
| UNKNOWN alternatives (3–5) and seeded variants | Wrapper | `unknown_variants.py`. Same RNG seed gives the same variants (tested). The variant mapping is in each manifest. |
| Pilot 10 rounds; real 20–30; ceiling 40 | Config + wrapper | `limits.yaml`; `plan.py` validates; `mirofish_api.py` refuses more than 40. Upstream may end a run early if its generated config has fewer hours than the rounds asked for; the rounds value is a maximum. |
| Runs: 2 per question, 3 above the UNKNOWN threshold | Config + wrapper | `limits.yaml` `runs`; `plan.py`. |
| `max_llm_calls` and `wall_clock_minutes` caps; cut rounds first, then runs, print cuts | Config + wrapper | `plan.py` (tested for order). During a batch, `run_batch.py` checks the caps between runs only. A run that has started is not stopped by a cap. |
| Planner inputs: seed size, entity count, question horizon, tokens/s | Wrapper (deviation) | The planner uses the pilot's measured calls, time and agent turns instead, which already reflect seed size, agent count and machine speed. Question horizon is **not** used: MiroFish's config generator picks the simulated time per round itself. |
| Agent cap | **Not enforceable** without changing internals | Upstream turns every typed graph entity into an agent and exposes no cap. `plan.py` and the pilot warn above `caps.max_agents`. The control is trimming the seed. |
| Pilot first, stop for confirmation | Wrapper | `run_batch.py run` needs `pilot.json` and `--confirm`. |
| Manifest: commit, model name and file sha256, config, seed hash, variant mapping, rounds, timings | Wrapper | `run_batch.py`. The model file hash is the sha256 of the GGUF blob in Ollama's store, plus Ollama's manifest digest. |
| Resume, skipping completed runs | Wrapper | `run_batch.py` and `mirofish_api.py` (tested, and verified by killing a live batch). |
| Metered calls without logging content | Wrapper | `llm_meter.py` on loopback logs time, status, token counts and JSON validity only. |
| factguard: numbers, dates, entities in report and transcript; UNKNOWN stances vs variant | Wrapper | After the run only. In-loop fact checking is out of scope. Entity and date checks are heuristics (capitalised words, English month names). |
| compare: rubric trajectories, resistors, UNKNOWN correlations, noise warning | Wrapper | Warns when identical-seed runs end differently ("mostly model noise"), when no variant ran twice, when the labeller disagrees with itself, and always below 5 runs. |
| Single-platform runs | **Not usable** | Upstream's Twitter-only and Reddit-only runners never log the end of rounds. Only `platform: parallel` works. |
| Simulated day starts at 08:00 | Wrapper | `run_batch.py` shifts the generated schedule in `simulation_config.json` before the rounds start (`sim_schedule.py`). MiroFish code is unchanged. |
| Stance of UNKNOWN actors follows the variant | **Not enforceable** without changing internals | MiroFish's config generator assigns stances itself and sometimes contradicts the variant. factguard flags it afterwards. |
| Reproducible runs | **Not enforceable** | Inputs, variants and plans are deterministic and hashed. The LLM sampling inside MiroFish is not seeded, so identical inputs give different runs. |
| No secrets in the repo | Process + `.gitignore` | `.env`, mappings, seeds and runs are git-ignored. `LLM_API_KEY` is a dummy value for Ollama. |
| Project folder not cloud-synced | Wrapper (warning only) | `cloud_sync_reason` in `_common.sh` checks the real path for `~/Library/CloudStorage`, iCloud Drive, and Google Drive or Dropbox marker files in parent folders. It cannot see every sync or backup tool. |

## 11. Known limits of using upstream MiroFish

Out of scope, as agreed (each would mean changing or replacing MiroFish internals):

- Replacing MiroFish's simulation engine (OASIS).
- Changing the agent platform from the social-media model: agents post, comment, like and follow on simulated Twitter and Reddit. Meetings, negotiations and votes exist only as things agents post about.
- Per-role model assignment: every agent, and every stage, uses the same model.
- Event-triggered agent activation: agents act on a probabilistic hourly schedule, not in response to events.
- In-loop fact checking: factguard checks after the run, and nothing stops an agent from inventing a figure mid-run.

Also observed with the pinned upstream:

- Only `platform: parallel` works (see the table).
- Agents are all typed graph entities. There is no cap and no way to add an actor except through the seed.
- MiroFish's config generator can override a variant's premise when it writes stances.
- The report agent states activity that never happened and adopts claims embedded in the seed (`INJECTION_TEST.md`).
- In `actions.jsonl`, the first active round repeats round 0's initial posts. The SQLite post tables, which `transcript.json` is built from, are correct.
- Runs are slow on a laptop (about 30 seconds per round with 9 agents on an M3 Max, more with more agents), so samples stay small.

**Kill and resume** (batch `phase5-resume`, 2 questions × 1 run × 10 rounds, pseudonymised):
- The batch process was SIGKILLed while the first real run was in round 2.
- Re-running the same command skipped the five finished stages and reused the same project, graph and simulation ids. It did not restart the still-running simulation, and continued at 40%.
- The second run then started fresh, and MiroFish's project count grew by exactly one.
- A third invocation skipped both runs ("already done").

**Purge:** `purge.sh phase5-resume --batch --yes` with MiroFish running. Afterwards the workspace had no `ops/runs/phase5-resume*` directories, no mapping file, no upload directories for the batch's 3 projects, simulations or reports, and no rows for its 3 graphs in any local-store table.

That purge also found that Google Drive for Desktop was backing up `~/Documents`, where this checkout lived. 15 recently written files had a second hard link in Drive's upload queue. The batch used only the fictional test seed, but this is why section 1 says to keep the project out of synced folders.
